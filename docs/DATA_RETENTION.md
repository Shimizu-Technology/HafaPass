# HåfaPass data retention schedule

**Engineering draft, 22 October 2026. Counsel and CPA confirmation required before live purge is enabled.** The executable table inventory is [`hafapass_api/config/data_retention.yml`](../hafapass_api/config/data_retention.yml). It classifies every database column and names each application table’s trigger column, period, action, and explicit PII clearing list. `orders` has a stricter four-way classification: `provider reference`, `money`, `pii`, or `non-personal`. Every provider reference blocks pending-order purge. New columns must be classified before the coverage spec passes.

| Record class | Clock starts | Proposed period | Expiry action | Reason to confirm |
|---|---|---|---|---|
| Completed orders, payments, refunds, disputes, payouts, settlements, fees, tax and audit records | End of the calendar year of completion, payment, certification, or creation as configured | 7 years after year end | Remove personal fields; keep amounts, status, identifiers and accounting links | Accounting, tax, chargeback and audit evidence. CPA and counsel must confirm the exact records and start dates. |
| Buyer details on a completed order, tickets and answers | End of the completed order's year | Up to the financial retention point | Anonymize | Order totals and admission evidence remain useful without buyer contact information. A verified deletion request can anonymize earlier if there is no hold or unresolved money operation. |
| Organizer tax/TIN and payout identity | End of the year of certification or payout | 7 years after year end | Anonymize tax identity and payee snapshots; keep transaction totals | W-9 and payout evidence may have different legal periods. Confirm with CPA. |
| Marketing withdrawal proof | Withdrawal time | 3 years | Delete | Retain evidence of the opt-out for three years. A deletion request also creates a permanent HMAC email suppression digest so later transactional and marketing sends to that address are blocked without retaining the address. |
| Unlinked marketplace analytics | Event time | 13 months | Delete | Existing analytics limit; linked order attribution follows the financial record. |
| Private organizer sales exports | File creation | 2 days | Delete S3 object and request row | Existing two-day export window. Active legal holds stop both the cleanup job and orphan sweep. |
| Abandoned or expired pending orders with no captured money or tickets | Expiry or abandonment | 90 days | Delete dependent checkout and inventory records, then order | Remove unused buyer contact details; any payment, refund, ticket, request or legal hold blocks disposal. |
| Active user accounts and organizer operating data | While account or event remains active | No automatic account deletion | Keep; handle verified request | Automatic inactivity deletion could interrupt tickets, membership, event operations or payouts. |
| User uploads in S3 | Account or event lifecycle | No automatic account deletion | Delete on an eligible verified deletion request | An upload may be a live event asset. Counsel should set a post-event period. |
| Scanner and device evidence, operational review records | Creation or event activity as configured | 7 years where audit evidence; otherwise event lifecycle | Keep or anonymize as configured | Scanner admission evidence can matter in refunds or disputes. Device local storage also needs an operator policy. |

The `keep` action means the financial or audit row remains after its seven-year review point. It does **not** mean all personal details remain: the order, payout, tax, audit, delivery and admission anonymizers remove the fields named in the configuration. Some event or account records remain active until a separate closure decision; the proposed period needs counsel review. The schedule is deliberately conservative where a row participates in payment, audit, admission, or event integrity.

The refund reconciliation queue added by #139 uses existing refund, dispute, event-change response, cancellation refund item, audit-log, and message-delivery tables; it adds no database columns. Reconciliation audit records are linked to their underlying orders for legal holds and deletion. Cancellation item error text, refund failure details, and stored digest snapshots are cleared only when every related order is eligible. A hold or unresolved money on any order represented in a shared digest stops that digest from being cleared.

The retention guard resolves direct foreign keys and nested structured `metadata`, `details`, and provider `payload` references. It follows `order_id` and `order_reference` (including digest `items`), plus refund, payment, dispute, payout, ticket, ticket-transfer, message-delivery, event-change, and settlement IDs back to their orders. It checks holds and unresolved money again under the row lock immediately before a write.

## Operation

`DataRetentionPurgeJob` runs daily through Solid Queue in batches of 100. It logs table counts and dry-run state only. Destructive retention requires **both** `site_settings.retention_purge_enabled = true` (set by an admin in Settings) **and** `DATA_RETENTION_DESTRUCTIVE_ENABLED=true` on the server. The environment variable is intentionally absent from production configuration. If it is unset, scheduled retention purge counts eligible rows and privacy execution returns a preview with zero writes and zero provider calls, even when an admin submits `confirm_dry_run`. `DATA_RETENTION_DRY_RUN=true` forces dry run regardless of both controls. Admin confirmation cannot override any dry-run control. The admin UI displays “Deletion is disabled on this server” while destructive retention is disabled. **The pre-existing two-day organizer sales-export S3 cleanup jobs from #135 and 13-month unlinked marketplace analytics purge are independent of these retention controls: they continue deleting expired records during dry run, but skip records covered by legal holds.** Before setting `DATA_RETENTION_DESTRUCTIVE_ENABLED=true` in production, run an independent review of the destructive paths and a staging rehearsal. Enabling or disabling the admin setting is audited. A hold on an organization, event, order, user, or buyer email prevents purge and deletion for matching records. Open disputes, pending refunds, unresolved reconciliation, and pending or held payouts block order anonymization and a deletion request.

The admin privacy queue shows what a request will anonymize, delete, retain, and why. An admin verifies the requester before execution. Guest requests require a one-time code sent to the order buyer email; an order link alone does not verify identity. Access exports use a seven-day signed JSON download link. If S3 or Clerk removal fails or is not configured, the request records a manual completion step in the queue. The operations owner must resolve those steps and confirm the provider result; a partial status is not complete erasure.
