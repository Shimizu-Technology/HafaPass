# Financial reversals and admitted inventory

Successful refunds and lost disputes record the financial result without treating it as evidence that a guest exited. Previously admitted tickets keep sold capacity and their active assigned seat. An append-only retention record identifies the originating succeeded refund or lost dispute and its reconciliation exception. Resolving that exception or recording Undo does not release the retained inventory or permit re-entry. This release adds no manual inventory-release command.

The `20261011150000` migration preserves the earliest existing admission evidence and adds durable history for legacy check-in paths. Its `down` operation refuses to remove either populated retention records or any non-null `tickets.first_admitted_at`. Check-in followed by Undo can leave that timestamp as the only admission evidence, so an empty retention table alone does not make a database rollback safe. A database with neither type of evidence can still roll the migration down and up.

Legacy Undo preserves a known check-in timestamp or the earliest accepted action's server receipt time before clearing the current check-in state. The domain method refuses Undo for a used legacy ticket with no timestamp, accepted admission history or existing retention record; it keeps the used state for organizer review rather than inventing a date or inferring physical exit. An existing retention record can support Undo without a historical date because it continues to reserve inventory and deny re-entry. Public scanner Undo already requires an accepted admission action; the additional refusal protects the domain/operator boundary.

An application rollback must preserve this schema and continue recording first-admission history, reserving entry during cumulative full-value pending refunds, enforcing retained-ticket admission/artifact denial, and retaining occupied inventory when refunds or lost disputes complete. A release from before these controls is an unsafe application rollback target even if the new database columns and table are left intact: it can ignore the retention journal, restock admitted tickets, or lose admission history after Undo.

Use a compatible application release or a forward repair. Preserve admission timestamps, retention records, signed provider receipts and original operation identities during incident handling; do not delete evidence or infer physical exit to make rollback possible. Follow the [operations incident procedures](OPERATIONS_RUNBOOK.md) for any required containment. These compatibility requirements do not grant production approval or authorize changes to live records.
