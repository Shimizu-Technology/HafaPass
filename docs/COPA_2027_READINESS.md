## Rush rehearsal and temporary compute

Use an isolated staging service with a distinct origin, its own Neon database, test credentials and `[LOAD TEST]` fixtures. The first candidate to measure is Render **2 CPU / 4 GB (`2c-4g`, formerly Pro)** in Singapore, with `HAFAPASS_RUNTIME=embedded`, `RAILS_MAX_THREADS=8`, `DB_POOL=15` and one Puma process. That pool satisfies the runtime's eight request threads plus six reserved connections minimum. The current Puma config pins worker count to zero. The FD split-worker template requires a code change before it can exercise two Puma workers. Use it only if profiling supports the topology and staging proves the handoff, pool budget and recovery. [Render compute plans](https://render.com/docs/compute-plans)

- Run shared-NAT and distributed buyer traffic with **600 concurrent buyers** reading the listing and event page and submitting checkout, with **3–5 signed-in scanners** independently syncing on the same fixture. Use real Stripe test-mode hold creation and an additional bounded saturation fixture small enough to sell out. The FD harness is a starting point. It measures a different workload and has no scanner actors. Drive scanner traffic alongside it, and tag event-detail latency separately from listing latency. Ensure each scenario starts with fresh fixture inventory.
- Pass thresholds are listing p95 below 300 ms, order p95 below 1.5 s, zero oversell, deadlocks, unexpected 429s or 5xx. Check paid holds, successful ticket issuance, expired inventory returned within the expiry job window, scanner queue drain and final server-confirmed counts. Hold at least one test across a short network interruption.
- Record application SQL time, Puma queue time and CPU/RSS, Stripe latency, Neon connection use, waits for event and pass-row locks, shared-IP throttle bucket writes, and oldest queue age. Start with production rate limits. If the shared-NAT rehearsal hits them, measure the actual one-minute request and held-ticket totals before selecting ceilings. Keep per-buyer controls and reconcile inventory after every run.
- Historical FD local runs at 200 VUs reported roughly 4–6 seconds checkout p95. The shared-NAT run without 429s recorded 3.73 seconds for orders and 4.46 seconds for listing. It measured pass contention and established zero oversells for its own fixture.
- A new Mac mini loopback run on the `a23cfa95` code used 600 shared-IP VUs, one request sequence per buyer, eight Puma threads, a 15-connection pool, PostgreSQL-backed rate counters and an order IP ceiling of 650/min for the run. The Rails test cache was disabled. The p95 results were 2,412 ms for listing, 2,728 ms for event detail and 7,076 ms for free orders. Both required timing thresholds failed. The 200-ticket fixture issued exactly 200 tickets, with 400 recognized sold-out responses, zero 429s and zero 5xx. Hosted latency, paid holds and scanner traffic remain unverified.
- Leon can switch to the **staging-proven** plan and environment on January 3 for January 4–10 on-sale week and January 24 for January 25–31 event week. Restore the baseline after each window when traffic and jobs have drained. Confirm readiness, scanner sync and queue activity after each change.
