# Never-fulfilled captures: A1 and A2 release runbook

This runbook covers the two A1 releases of [the never-fulfilled design](./design/never-fulfilled-captures.md) (§10). Home base runs the production release and every production command below. Agents never read or change production data. Every command here is read-only, except the deploys themselves. Nothing here changes an environment variable, a `SiteSetting` or Render configuration. Nothing makes a real charge or repairs a production row by hand.

## What each release does

| Release | Change | Money it can send for a fenced payment |
| --- | --- | --- |
| **A1-R1** (merge of #248) | Migrations `20261126100000`…`20261126140000`: classification, postings, repayment operations, the database **repayment fence** on `refunds` and `payouts`, and the **evidence guards** of the A1-R1 review and recheck (below). `Commerce::BuyerRepayment::SUBMITTER_ACTIVE = false`. | None. R1 reserves no repayment operation and never passes the operation gate. It can look up an older release's refund by its key and record the result (`Commerce::RepaymentAdjudication`). |
| **A1-R2** (small follow-up PR) | Changes `SUBMITTER_ACTIVE` to `true` and the specs that assert R1 behaviour. Nothing else. | One repayment operation at a time per payment, sized under the order lock and rechecked at the gate. |

**A2 (operational readers, design §8.10.9).** Migration `20261126170000` adds `hafapass_overpaid_platform_only` and redefines `hafapass_payout_block_start` so an unproven `never_fulfilled_buyer_overpaid` holds payouts and finalization (an older release then fails closed on those events), and adds `stripe_fee_evidences.facts_recorded_at` with its stamping trigger. Before the A2 deploy, add to the read-only evidence: the count of open `never_fulfilled_buyer_overpaid` items and how many are proven (`SELECT count(*) FILTER (WHERE hafapass_overpaid_platform_only(payment_id)) FROM reconciliation_exceptions WHERE status = 0 AND code = 'never_fulfilled_buyer_overpaid'`); events with a classified capture whose latest finalized settlement predates A2 (they need a new version); `classified_linked_adjustment` alerts; and `bin/rails stripe_fee_evidence:stamp_facts` (dry run) output. After the deploy and drain, the authorized release runs `payout_custody:derive` (with `AUTHORIZED_BY`) and `stripe_fee_evidence:stamp_facts` with `DRY_RUN=0` ("A2 release" below). Rollback: `db:rollback` of `20261126170000` restores the A1-R1 hold function and drops the column; no row depends on it.

A *fenced payment* has a `never_fulfilled_captures` row or an exception with one of these codes: `late_payment_success_after_inventory_release`, `late_payment_success_after_hold_expiry`, `pass_all_included_nights_cancelled`, `unfulfilled_second_capture`, `never_fulfilled_ownership_ambiguous` or `never_fulfilled_classification_quarantined`. The open or resolved status of the exception does not matter. The database function `hafapass_fenced_payment(payment_id)` is the single definition, and the application uses the same function.

## The fence (installed by R1's pre-deploy migration)

`bin/release-migrate` runs before any R1 process starts, so the fence exists before the overlap begins.

- **`refunds_repayment_fence`** rejects two things for a fenced payment. The first is a new outbound reservation: a row with no provider refund ID, no repayment operation and a key that is not `provider:stripe:refund:*`. The second is the last local gate: moving such a row's `failure_code` to `provider_result_unknown`, which 7bcd97c2 persists immediately before its Stripe POST. A row that belongs to a repayment operation passes the gate only while that operation is `submitting`, and only `Commerce::BuyerRepayment.gate!` sets that. The fence never rejects provider evidence: inbound rows keyed `provider:stripe:refund:<id>`, rows that carry a provider refund ID, and outcomes of a row already past the gate.
- **`payouts_repayment_fence`** rejects creating a payout as `pending` or `processing`, releasing a held payout, and submitting a pending one, on an event with an open blocking never-fulfilled item. `never_fulfilled_buyer_overpaid` never blocks (P4). The application checks the same rule first (`Commerce::NeverFulfilledPayoutHold`) and also guards paid recording. A transfer that left before a cancellation can still be recorded with the existing confirmation.

An old worker that hits the fence fails before any network call. Its job retries and fails again. Its exception stays open, which keeps the event's payouts and finalization blocked.

## The evidence guards (installed by `20261126130000`, `20261126140000` and `20261126150000`, before any R1 process starts)

Each guard sits on the write that causes the effect, so a 7bcd97c2 writer, a rollback build or raw SQL fails in the same transaction. A refused webhook rolls back whole; its signed receipt stays `failed`, Stripe redelivers it, and R1 applies it. The provider fact is never lost.

| Guard | Refuses | Allows |
| --- | --- | --- |
| `refund_items_sale_ownership`, `promoter_commission_entries_sale_ownership`, `ticket_inventory_retentions_sale_ownership`, `tickets_dispute_sale_ownership` | Refund items, commission reversals, retained inventory and dispute ticket cancellation from a payment that does not own the sale (`hafapass_sale_owner_payment`: the order's recorded fulfilling payment; an order-scope never-fulfilled capture; else the order's only captured payment of its mode, and for a fenced payment only when the order never fulfilled) | Everything on the owning payment. R1 records the non-owner's refund or loss itself and holds the sale effects (`never_fulfilled_sale_effects_held`) |
| `payouts_repayment_fence` (replaced twice) | On an event with an open blocking item or an overlap capture (`hafapass_payout_block_start`): creating a payout, releasing a held one, moving one to `processing`, and recording one `paid` from any release, including 7bcd97c2 with a pre-hold submission and whatever transfer time it is given | `pending → processing` for a submission authorized **before** the earliest item (the in-flight outcome). `paid` only with that pre-hold submission, `paid_at` before the earliest item and this release's verified confirmation in the same transaction (`PayoutReconciler` with `sent_before_hold_confirmed`): money that already left is recorded, never a new payment. Holding, failing and reversing |
| `audit_logs_payout_submission_fence` | The actual submission authorization of both releases (the `payout.submission_requested` audit, written under the payout lock before the gateway call) on such an event | — |
| `settlements_finalization_fence` | Finalizing a statement on such an event; and on an event with a never-fulfilled order in a sale status, any finalizer except R1's reader (`hafapass.settlement_reader`) | R1's `Settlements::Finalizer` |
| `payouts_repayment_fence` (insert) | Creating a payout on an event with a never-fulfilled order in a sale status, except by R1's `PayoutCreator` | — |
| `reconciliation_exceptions_evidence_hold` | Closing an evidence hold (`FinancialIntegrity::EVIDENCE_HOLD_CODES`) unless the same transaction's evidence path named it: a note, the 7bcd97c2 admin action or raw SQL cannot | The evaluator, reconcile, `SaleEffectHold` |
| `refunds_identity_fence` | Binding a provider refund ID to an outbound row of a fenced payment unless the application matched it exactly (its POST response, a lookup by its own key, its provider ID); never by amount and date | Inbound rows keyed `provider:stripe:refund:<id>` |
| `orders_sale_refund_aggregate` (recheck) | Once another payment on the order has a succeeded refund: an order refund total above what the sale's own payment returned, or a move to `refunded` it does not cover (7bcd97c2's order-wide same-mode sum) | Everything on single-payment orders, and every total that counts only the owning payment's refunds (R1's sum). The refused notice stays `failed`; R1 records the exact partial return from the redelivery, finding the old pending row by its `provider:stripe:refund:<id>` key |
| Overlap captures in `hafapass_payout_block_start` (recheck) | Payouts, submissions and statements on an event with a capture recorded since A1 that no release classified, on an order another payment fulfilled or a sold order with another capture (7bcd97c2 acknowledges such a capture silently) | Everything once R1 classifies it from its own signed receipt or quarantines it (`RefundReconciliationJob`, a redelivered notice, or reconcile) |
| `webhook_events_keep_identity` (recheck) | — (never refuses) | Clearing a signed receipt's payload from any release keeps its provider identity in the non-personal columns |
| Overlap captures on a marked order (boundary) | The same, for a capture 7bcd97c2 acknowledged on an order already marked never fulfilled, in any status (a refund on the first capture moves it to partially refunded or refunded) and any mode | Everything once R1 classifies it as another order-scope capture from its signed receipt, or quarantines it. Its own exception keeps the event held after the first capture is repaid |
| `reconciliation_exceptions_hold_start` (boundary) | Changing an exception's `hold_started_at`. A writer cannot supply one | Stamps the earliest overlap start of any unclassified capture on the payment's order, or of another blocking item still open on the payment. Classification and quarantine therefore keep the original payout cutoff, in either order. A capture from before the cutover counts as the earliest competitor (design §6.10) |
| Event lock in the payout fences (boundary) | 7bcd97c2's payout creation, submission, outcome, paid recording, release or finalization while a capture, checkout or other event writer holds the event row: refused at once (SQLSTATE 55P03, "has a sale or capture in progress"). It never waits, because the old writer already holds the payout | Everything once the event is free; the fence then reads a snapshot that includes every committed capture. R1's writers lock organization → event → payout first and wait for the capture instead |

The settlement reader rule exists because 7bcd97c2's calculator disagrees on a never-fulfilled order: for the review's $13.60 order ($5 refund, $8.60 loss) in an event with a $99.00 sale, it reports $97.29 payable, and R1 reports $99.00. Without the rule, a rollback could finalize and pay the old figure.

**What the fence cannot stop.** An old worker retrying a request that was already past its gate before the migration committed resends **the same idempotency key** (`late-capture:payment:<id>`). Stripe returns the first result for that key. 7bcd97c2 refuses to resend after 23 hours. That request is exactly what boundary item 4 below adjudicates. New operations never use that key (operation *n* uses `late-capture:payment:<id>:op:<n>`), so an old worker can never find or co-send a new operation.

## Before A1-R1: record the baseline

```sh
psql "$READ_ONLY_DATABASE_URL" -v ON_ERROR_STOP=1 -f hafapass_api/script/never_fulfilled/baseline_before_r1.sql
```

This records:

- late-capture exceptions by code and status;
- finalized settlements on their events;
- pending, processing and held payouts on those events;
- refunds in `provider_result_unknown`;
- late-capture-key refunds by status.

Also save the CPA and BPT CSVs and their sha256 for every month with live activity, using the existing admin exports. R1 **does** change two readers relative to 7bcd97c2, so compare like-format monetary rows, not only hashes:

- `Settlements::Calculator` leaves an order-scope never-fulfilled order's proceeds, refunds, refund items, losses and platform fees out (its processing keeps the never-fulfilled bearer rule), and counts only the recorded fulfilling payment's refunds and disputes on the sale.
- `CpaMonthlyReport` books never-fulfilled captures as buyer refund captures, not organizer custody or chargebacks (earlier A1 commits).

Expected after R1: identical rows and hashes for every month and event with no never-fulfilled activity. For an event with a classified order, only that event's row and the month's total row differ, and the R1 values agree with the R1 calculator. The two-process rehearsal shows the pattern: `chargebacks 8.60→0.00`, `closing_custodial_liability 50.60→59.20`, `buyer_refunds_paid 4.42→12.00`, `closing_buyer_refunds_owed 7.58→0.00`, flag `no→yes`; BPT identical. Any other difference is a defect. Also save the baseline's `payout_transitions_on_late_capture_events` (all payout transitions ever audited on those events), so the post-R1 check compares history and not only what is blocked now. The upgrade itself changes no export: the two-process rehearsal exports CPA and BPT from 7bcd97c2 on its own schema and data, migrates, and exports again from R1, with identical rows and hashes.

## After A1-R1 is live

Use the read-only rake task. It runs the same SQL in one `READ ONLY` transaction and rolls it back:

```sh
bin/rails never_fulfilled:release_evidence R1_SHA=<40-hex R1 commit> R1_LIVE_AT=<ISO-8601 UTC time R1 went live>
bin/rails never_fulfilled:verify                        # read-only reconcile counts
bin/rails never_fulfilled:reconcile                     # DRY_RUN=1 is the default: counts only
```

`psql` gives the same output: `psql "$READ_ONLY_DATABASE_URL" -v r1_sha=... -v r1_live_at=... -v bound_seconds=770 -f hafapass_api/script/never_fulfilled/release_evidence.sql`. The bound is `Commerce::BuyerRepayment.in_flight_bound`, which is 770 seconds with the current `config/initializers/stripe.rb` values. Read it from the code if those values change.

Check:

- `triggers` lists all 27 triggers, including `refunds_repayment_fence`, `payouts_repayment_fence`, `repayment_operations_check`, the eight evidence guards above, `orders_sale_refund_aggregate`, `webhook_events_keep_identity` and `reconciliation_exceptions_hold_start`.
- `unvalidated_constraints` is empty, and `cutovers` contains `a1_capture_recording`, `a1_return_recording`, `a1_repayment_fence`, `a1_evidence_guards`, `a1_overlap_guards` and `a1_boundary_guards`.
- `payouts_on_blocked_events.changed_since_r1` is 0 for every row, and `payout_transitions_since_r1` shows no `payout.submission_requested` or `payout.paid` on an affected event, and `payout.processing` only as the outcome of a submission authorized before its hold.
- `paid_under_hold` lists every payout recorded paid while its event was held. Each row must show `submission_requested_at` and `paid_at` both before `hold_started_at`, `transfer_before_hold = t` and `sent_before_hold_confirmed = true`. Check each against the bank record.
- `overlap_captures` is empty, or each row is classified or quarantined by the next `RefundReconciliationJob` run; `never_fulfilled:verify` prints `overlap_captures=0`.
- `orphan_receipts_without_identity` lists orphan notices whose payload was cleared before A1-R1; finance records a disposition for each (Verify, or a note with its confirmation).
- `evidence_hold_resolutions` shows only evaluator, reconcile or `sale_effects_released` resolutions, never a manual one.

Disposition the reconcile dry run's quarantined and restatement counts as §4.5 requires. No restatement is ever written.

## Release boundary for A1-R2

Deploy R2 only when items 1 through 6 hold, including 3a.

0. **R1 itself holds.** R1 never sends a repayment and never needs drain evidence. If anything below cannot be shown, stay on R1; it is the safe state.
1. **Writers and fence present.** The evidence run shows every trigger, validated constraints and the four cutovers. CI passed on the R1 head, including `spec/models/repayment_fence_spec.rb` and `spec/services/commerce/buyer_repayment_concurrency_spec.rb` (M-05…M-08), plus the previous-release rehearsal below.
2. **No new submitter during the overlap.** This is a property of the R1 code: `SUBMITTER_ACTIVE = false`, and the specs that run as R1 assert zero POSTs. It is not a runtime setting.
3. **Old processes gone.**
   - (a) Render, read-only, through home base: the R1 deploy is `live`, every earlier deploy is `deactivated`, no instance runs an earlier commit, and more than Render's shutdown grace plus 23 hours and the in-flight bound has passed since R1 went live (the last time a 7bcd97c2 process could still resend a request it had in hand).
   - (b) `live_processes` shows only `other_revision = f`, and `claimed_by_other_revision` is 0. `runtime_ticks` shows recent R1 ticks for every required task.
4. **Durable work audited.**
   - `refund_jobs_before_r1` is empty: no unfinished `LateCaptureRefundJob`, `EventCancellationRefundJob` or `RefundReconciliationJob` was enqueued before R1 went live.
   - `legacy_refunds_on_fenced_payments` is empty. Each such refund has been adjudicated by a lookup at Stripe that **started after** its `adjudicable_after` time, its last possible send: `created_at` + 23 hours (7bcd97c2's own replay window, checked just before its gate) + the in-flight bound, never earlier than its recorded submission + the bound. The submission audit alone is not that boundary: 7bcd97c2 can pass its gate again for a row already marked unknown without writing anything. R1 enqueues `RepaymentAdjudicationJob` for each one when a repayment waits on it, or when an administrator uses **Refund buyer**, and the job waits until that time. A row with `adjudicable = f` may still land at Stripe and is never treated as absent. A Stripe refund found by the row's own key is recorded at any time.
   - Every pending refund on a fenced payment was checked by its own key only. **Check Stripe status** and the scheduled refund resync never match a fenced row by amount and date, and a Dashboard refund without the key is recorded as its own movement (**Verify**).
   - `never_fulfilled:verify` reports `unclassified_or_unposted=0`, `unposted_movement_payments=0` and `overlap_captures=0`, and every `orphan_receipts_without_identity` item has a finance disposition.
5. **Payouts fail closed.** Events with open blocking items still show them. No payout on them moved since R1 (`changed_since_r1 = 0`), except a pre-hold submission's `processing` outcome and a `paid` recorded by R1 with its pre-hold transfer evidence (`paid_under_hold`).

**What each item proves, and what it does not.** 3b is evidence from the queue tables: a heartbeat and an empty pending-row query cannot prove that an old web process or an in-flight HTTP request is gone. Neither 3a nor 3b is used by the code. R1's safety during the overlap does not depend on drain: every old effect path above is refused by the database, and adjudication waits for each row's own last possible send, which comes from 7bcd97c2's code, not from a drain observation. R2 needs drain (3a) because R2's own operation gate resends an `unknown` operation after the in-flight bound, which is safe only once no old sender can hold the same key. If 3a is unavailable, do not deploy R2; there is no fence-only alternative.

6. **Backlog listed.** `bin/rails never_fulfilled:repayment_backlog` (read-only `DRY_RUN=1`, the default) lists each classified capture R1 left waiting, with what is owed and its wait reason.

### The R2 change, exactly

- `hafapass_api/app/services/commerce/buyer_repayment.rb`: `SUBMITTER_ACTIVE = false` becomes `SUBMITTER_ACTIVE = true`.
- Specs: examples that assert R1 behaviour (`"A1-R1"` describe blocks and `sends nothing in A1-R1` examples) either move under `repayment_submitter: :active` or are deleted. The `repayment_submitter: :active` tag becomes the default.
- No migration, setting, environment variable or other code change. If R2 needs more than this, it is a different release and needs its own review.
- After R2 is live and the boundary items still hold, home base runs `bin/rails never_fulfilled:repayment_backlog DRY_RUN=0` once. It enqueues `LateCaptureRefundJob` for each owed capture; R1 code refuses that mode. Each job reserves under the order lock and the gate rechecks everything, so a second run is harmless.

## Two-version rehearsals (before each production deploy)

On task-owned localhost databases:


**Two processes on one database** (`rehearse_two_process.sh`). The pinned 7bcd97c2 app (exported with `git archive`, no checkout) and this release run as separate `bin/rails runner` processes against one database with this branch's schema. Stripe and the payout gateway are stubbed (`two_process/stubs.rb`); a JSON ledger shared by both processes stands in for Stripe, so what one process POSTs the other finds by its key. The old process is paused inside its stubbed calls: after its last refund gate (in the POST), at its lookup before the gate, and at the payout gateway after its submission authorization. It writes every provider call, every action and its result, CPA/BPT rows and the release evidence to the scratch directory, and drops the database unless `KEEP_DB=1`. It starts from 7bcd97c2's own schema with data that release wrote (a live sale with a partial refund and two orphan refund notices, one already cleared), runs this branch's migrations on it as `bin/release-migrate` would, and ends with an `assertions` step that checks the saved ticket, inventory, refund, posting, classification, payout and export postconditions (`assertions.txt`; any `FAIL` exits nonzero). The new suite also runs the verbatim 7bcd97c2 `RefundCreator`, `LateCaptureRefund`, `PayoutCreator`, `PayoutReconciler`, `Settlements::Finalizer`, `Settlements::Calculator` and `OrganizationPayoutBalance` (`spec/support/legacy_7bcd97c2/`) against the new schema, including two-connection races.

## A2 release

A2 switches every finance reader to the classified-payment rules (design §8.10.6–8.10.9) and adds the payout entry and overlap fences (§8.10.11). Its pre-deploy migrations are `20261126160000` (frozen payout custody), `20261126170000` (P4 proof, fee fact times) and `20261126180000` (payout entry). The last one records the `a2_payout_entry` cutover. A2 follows A1-R2. This runbook does not change the R2 gate: R2 stays inactive until its own drain and adjudication evidence (above) is recorded.

What changes for running processes once `20261126180000` is in:
- On an event with a classified capture, only A2 may finalize, create a payout, release one from hold, authorize a submission, or record `processing` or `paid`. An A1 process gets "Payout entry fence: payouts on this event need the current settlement reader" and changes nothing.
- On every event, `paid` needs the payout's custody determination in the same transaction, and only A2 writes it. An A1 paid recording fails with "Payout custody fence". During the deploy overlap, do not record payouts as paid until A2 is serving. Release and submission on events without a classified capture keep working in A1.
- A payout approved on a version that predates a classified capture (every pre-A2 version on such an event) cannot be released or submitted. It is recorded paid only for a transfer submitted and sent before the version was restated, and never before the cutover (settlement operations doc, "A2 payout entry rules").

### Before the A2 deploy (home base, read-only)

1. Save the baseline exports. For every month with live activity, download the CPA monthly export and the BPT events export into one directory, keeping their file names (`hafapass-cpa-monthly-YYYY-MM.csv`, `hafapass-bpt-events-YYYY-MM.csv`). If production has no live-period activity (R1's release record found no live-period CSV baseline), save no CSVs. Instead, finance writes `VERIFIED_ZERO_BASELINE` in that directory with `reference=<finance ticket, e.g. FIN-2026-11-001>`, `verified_at=<ISO8601 time with offset>` and `evidence=<the read-only query and its zero result>`. Step 7 then reports `comparison=verified_zero_baseline`, never a row comparison. The candidate side of that check is the exporters' own pair for every month downloaded (step 7), so download both files for each month.
2. Run `bin/rails never_fulfilled:verify` and `bin/rails never_fulfilled:a2_preflight` and save both outputs. The preflight reads one read-only repeatable-read snapshot (`section=snapshot isolation=repeatable_read read_only=on`), and a guard passes only when its trigger is on its table and enabled for the session. Before the migration, the preflight's `section=guards` line shows `gate_guards=FAIL`, as expected. `section=undisposed` must already show `gate_zero_undisposed=PASS`: no unclassified or unposted captures, no overlap captures, no receipt without identity, no posting pending correction, no repayment operation or refund on a classified payment with an unknown result. If any count is not zero, stop.
3. For each `section=payout` line (pending, processing or held payouts on events with a classified capture), finance decides before the deploy, following its `action`. If the transfer already left, keep the bank reference and transfer time ready to record it. Otherwise it is failed and reissued after the deploy. Any `section=event` line with `over_committed=yes` stays held until finance reviews it (design §8.8).

### After the migration, during the overlap

4. `bin/rails never_fulfilled:a2_preflight`: `gate_guards=PASS` and `failing_guards=none`, with every listed trigger `true`, `reader_rule_current=true` and the cutover time. The list is every money guard the release depends on (`FinancialIntegrity::PREFLIGHT_TRIGGERS`), including both reversal checks, the return proof's insert and commit checks, the frozen settlement guard and the accepted-transfer guard; each must be on its table in the current schema, run its own function from that schema and be enabled for the session. A disabled, replica-only or rebound trigger fails the gate and is named in `failing_guards`.

### After drain (only A2 processes, as in R2's boundary items 3a and 3b)

5. Run `bin/rails payout_custody:derive` (dry run) and review the counts. Then write with `DRY_RUN=0 AUTHORIZED_BY="<finance ticket, e.g. FIN-2026-11-001>"`. It writes one `derived_history` row per payout recorded paid before the cutover that has none, keeps `AUTHORIZED_BY` in each row, and refuses without it or with anything that is not a structured finance reference (the row is immutable and holds no personal names). The write reports each row as saved. A payout whose funding or capture timing cannot be shown (`ambiguous`: no funded sale line, more paid than its lines, a capture recorded before A1 without a proved time, or a funded order classified since) is reported as `needs_published_baseline` and left undetermined. Finance supplies its published BPT treatment from the saved baseline exports (step 1) as `PUBLISHED_BASELINE=<csv>` with columns `payout_id,included,source`, authorized under the same `AUTHORIZED_BY`, and reruns the write. `source` is a structured reference, never free text or a preparer's name (it is kept in immutable evidence classified as holding no personal data): `bpt-export:YYYY-MM` for the filed BPT detail export of that month, optionally `bpt-export:YYYY-MM@sha256:<64-hex file digest>`, or `disposition:<finance ticket>` (for example `disposition:FIN-2026-11-002`). The parser and the write refuse anything else. Then `bin/rails payout_custody:verify` must show `undetermined_paid_payouts=0`; the ambiguous determinations are listed for finance.
6. Run `bin/rails stripe_fee_evidence:stamp_facts` as a dry run, then with `DRY_RUN=0` (tranche 4).
7. Download the same exports again into a second directory and compare them like for like: `ruby script/never_fulfilled/compare_exports.rb BASELINE_DIR CANDIDATE_DIR EXPECTED_FILE`. `EXPECTED_FILE` lists, one per line, `<file> <row key>` for each row the rehearsal diff says may change (rows of events with a classified capture, and their totals). The gate rejects unexpected differences (exit 0 and `unexpected_differences=0` only when every difference is listed): a row not in `EXPECTED_FILE` must match byte for byte in the pre-existing columns, while a listed row may change, be added or be removed. A pass therefore does not prove that every published cell stayed unchanged; finance reviews each listed difference the output prints (`CHANGED (expected)`, `ADDED (expected)`, `REMOVED (expected)`). A key that appears twice in either export is a difference. The two inventories must match: a CSV only the candidate has (a month the baseline never exported) is a difference unless `EXPECTED_FILE` authorizes it with a `<file> candidate_only` line, and its rows are listed either way. A missing directory or a baseline with no CSV (and no `VERIFIED_ZERO_BASELINE`) exits 2 and is never evidence. Every CSV in either directory must be well formed: unique, non-blank header names and every row exactly as wide as the header (an incomplete-export marker line fails this); otherwise the comparison exits 2. A `VERIFIED_ZERO_BASELINE` record compares no published rows (there were none); it proves only that the candidate's exports show no activity. Each file's header must be its exporter's exact, versioned full header (the output names it, for example `schema cpa-monthly-a2-1`), so a truncated export, a missing or duplicate monetary column, or a reordered or extra column exits 2. For every month the candidate holds, it needs both exports exactly as the endpoints write them: `hafapass-cpa-monthly-YYYY-MM.csv` with its one mandatory `total` row for that month, every amount zero, the exception flag `no`, no notes and the zero nonprofit count, and `hafapass-bpt-events-YYYY-MM.csv` with its header only. A month with only one of the two, two files of one kind, a CSV that is neither, or no CSV at all exits 2. Any nonzero amount or count, a second or non-total CPA row, a wrong month, or any BPT row exits 1. Review the appended columns separately. A changed published month is a correction for finance and the CPA (design §5.3), never a silent rewrite.
8. Run `bin/rails never_fulfilled:a2_preflight` again. For every event with `needs_finalizing=yes`, finance finalizes the statement again. Then each in-flight payout follows its `action`: record the transfer that left with `sent_before_restatement_confirmed: true` and its time, or fail the reservation and reissue it on the new version. `remaining_cents` shows what the organizer can still be paid. `gate_custody_complete=PASS` is required.
   When finalizing is refused because the event is held (an open `never_fulfilled_buyer_overpaid` whose platform-only proof a pending, processing or held payout on a version without the capture's `$0` line defeats), clear that payout first. Finance checks the bank: if no transfer left, record it `failed` (no return evidence; nothing moved), rerun the preflight, then finalize and reissue on the new version. A transfer that did leave stays on the evidence path above (`sent_before_restatement_confirmed` with its time, or the accepted-transfer and return-evidence rules), never `failed`. A payout already recorded `reversed` without return evidence (reversed before the capture was classified, or older history) defeats the proof the same way and cannot be changed: finance checks the bank statement and, when the full amount came back, attaches it with `POST /api/v1/admin/payouts/:id/return_evidence` (admin-only; `return_reference`, `returned_amount_cents` equal to the amount that left, `returned_at`, plus the usual `reference`, `reason` and `confirmed_at`). That is the authorized evidence-only disposition: it writes `payout.return_evidence_attached` and the durable return proof, changes nothing on the payout (status, amounts, `paid_at`, the reversal's CPA month), and is idempotent. The admin list flags such payouts `return_evidence_required`. If the bank shows no exact return, the event stays held as an explicit unresolved finance hold until the money is accounted for; never count unknown funds as returned.
   Before sending any manual transfer, reload Admin → Payouts immediately before sending and send only when the row says the approval is current. That status is a read-time verdict (`PayoutEntryGuard.dispatch`, computed when the list loads); it is not stored and authorizes nothing. A capture, refund or restatement can commit after the reload and before the transfer leaves, and HåfaPass does not cover that window. A transfer that has left cannot be recalled, and a later paid-recording refusal does not reverse it. An exceptional prior-send confirmation (`sent_before_restatement_confirmed`, or a stale-statement disposition) is API-only; before the first live use, an authorized operator rehearses that authenticated request on staging for a genuine pre-cutoff transfer, with no funds moved.
9. Statement UI check of the `$0` and "not counted" lines at 390 px and 1280 px (lead). A fixture check against responses generated by the real statement and payout-list services runs in Chromium at both widths (`hafapass_frontend/e2e/a2-review-ui.spec.js`; screenshots kept with the workstream's release evidence, outside the repository). It does not replace the authenticated check on staging.

### A2 accounting positions that stay open after release

- **Affected periods are provisional.** No explicit period close exists yet (`accounting_period_closes`, design §8.10.13). Until finance and the CPA approve that procedure and close a period with it, every month with classified-capture activity is provisional: a fact that becomes readable later (reconcile, a late posting) can still change an earlier, alerted month. The release comparison proves only that A2 itself moves no published pre-existing column.
- **Fee and tax treatment is a working default.** The fee and tax share of a classified capture (recognized at capture, reversed by its postings, P2 for lost disputes) and the `item_record` allocation (P9, including the 75¢ mixed-cart example) need CPA confirmation before they are relied on for filing.
- **Reversals on events with a classified capture.** A reversal there is recorded only with the bank's exact return evidence (`return_reference`, `returned_amount_cents` equal to the amount that left, `returned_at` after the transfer left and not in the future; API-only, the admin dialog has no return fields). Without it the payout stays paid and its amount stays committed. The database enforces this for every writer once `20261126180000` is in (`payouts_reversal_return_check`, checked when the transaction commits): an A1 process during the overlap, A1 code after a rollback, and raw SQL cannot commit a reversal on such an event unless the same transaction records that exact return, so A1's generic reversal fails and releases nothing. Record those reversals from A2. The P4 proof treats any reversal without that recorded return (history from before the migration) as money still with the organizer, until finance attaches the bank's exact return (step 8). The recorded return is kept as a durable, non-personal proof (`payout_return_proofs`: the amount that left, the transfer and return times, a SHA-256 digest of the return reference), which the proof and the fence read instead of the audit payload, so audit retention redaction never undoes it. The amount that left is the disbursement, or a check's audited adjusted amount; the return keeps the payout's real transfer identifier, and an accepted transfer's return is compared with the provider's reported paid time. A transfer that never left is recorded `failed`. Events without a classified capture keep their existing reversal accounting (a reversal releases the reservation on the generic confirmation); return evidence given there is verified the same way. Whether every reversal should need return evidence is a finance decision outside A2.
- **P4 hold start.** An over-return's hold starts when its proof first failed in the current episode and stays there until the proof recovers and a fence passes: the database checks the proof when it opens the exception (`proof_checked_at`, `hold_started_at`), so a refund pending since before the last passing fence that posts while a newer one is pending keeps the opening as the cutoff. An over-return opened before this release was checked is held from its opening (conservative). After the proof recovers, a later failure with no fence pass in between keeps the earlier start (conservative); a transfer sent in that window is recorded only after the hold resolves or with a finance disposition. The cutoff can also start earlier than the proof actually failed (CodeRabbit 4704933014): it is the earliest fact recorded after the last passing fence that can defeat the proof, in any state now, and the database cannot tell whether a fact that is resolved now (a refund created already posted, a posting created already recognized) ever defeated it. This is kept deliberately. It never sends early or releases money: dispatch shows "Do not send" from the moment the proof fails, the payout's amount stays committed, and any fence pass (a submission or a finalization) moves the anchor forward past such facts. Its only cost is availability: a transfer confirmed sent between such a fact and the real failure is not recorded paid until the hold resolves (then it records normally), and overlapping or continuous holds can never move the cutoff later. A durable record of when each fact began defeating the proof would be needed to narrow it; that is not part of A2.
- **Dispute fees are not booked.** HåfaPass stores no verified dispute fee, so A2 books none and invents none; finance uses Stripe's statement for them (P5).
- **Annual organizer view.** `TaxReports#organizers` keeps the payout population verified at `a0b25ffe`: paid USD payouts on events with a live or legacy capture from any provider, so an organizer-direct Clover event's payout is included and a test-only event's is not. Only the BPT detail CSV restricts payouts to Stripe custody (frozen determinations). The annual view is frozen against later activity: the capture must be recorded by the payout's paid recording (the conservative rule's bound, for any provider), or the payout's frozen determination records Stripe custody, so a later capture adds no earlier payout. An ordinary refund counts only on the sale's own payment (the fulfilling payment when recorded) or with no payment recorded; a refund on another payment of the order is not organizer activity. Every payment to a payee is the annual payee report's (`AnnualPayeeReport`). No CPA rule is adopted here, and the CPA workpaper's `organizer_payouts_made` keeps its own rule.
- **Organizer-borne processing on payment B.** A verified Stripe fee on an organizer-borne payment-scope capture has no fee component yet, so no line charges it. Its review blocks finalization and every payout entry on the event until finance books the exact cost. HåfaPass-borne, the default, holds nothing.
- **A transfer the provider accepted after a payout guard or fence refused paid.** This covers the repayment hold and a restatement (database fences) and, checked by this release under the same locks, an ordinary statement change and an open organizer-borne processing review. The acceptance is kept (in flight, with the provider's reference, amount and reported time in the conflict audit) and never sent again. A later provider result never downgrades it. Finance records it with the audited `accepted_transfer` outcome (acknowledging the conflict audit). It is never an ordinary paid payout and never failed. Its amount stays committed, so no payout, under the same or a fresh key, can send it again. The database enforces this for every writer and on every event once `20261126180000` is in (`payouts_accepted_transfer_guard`, on the durable `payouts.provider_accepted_at`): A1 during the overlap or after a rollback, and raw SQL, cannot record it paid, failed or pending, release its hold, change its identity or amount, delete it, or reverse it before the acceptance is recorded, and its reversal commits only with the current release's exact return proof. It is reversed only with the bank's exact return evidence (`return_reference`, `returned_amount_cents` equal to the amount that left, `returned_at` after the acceptance), and only after finance recorded the acceptance. When the bank's return arrives first, record `accepted_transfer`, then the reversal; the reversal is refused until then (the database refuses the other order for any writer), so the CPA workpaper books the outgoing transfer and its return once each. The CPA workpaper books it once in `organizer_payouts_made`, in the month finance recorded it, lists it with its identity in `accepted_transfers`, and books a verified return as a reversal. No current gateway returns paid, so this is latent until a provider adapter does; no real adapter behavior beyond these recorded facts is assumed.

`script/never_fulfilled/rehearse_a2_overlap.sh` (`REHEARSAL_DIR=<scratch> REHEARSAL_DB=hafapass_ncap_rehearsal_<name>`) runs both releases as separate processes, with Stripe and the payout gateway stubbed. The candidate's migrations then upgrade the database, and the steps run in the order listed in the script. The saved assertions:

- **M-09:** A1 finalization, creation (its own digest check, and its marked insert refused by the database), automatic held release, submission and paid recording are all refused on the affected event. On the plain event, A1 finalization, held release, submission and a marked insert are allowed. A1's late paid recording fails closed on any event ("Payout custody fence"), and A2 records the same transfer with its custody row.
- **Stale and matching versions:** A2 refuses held release (manual and automatic) and submission, refuses paid for a never-submitted payout, and refuses a transfer after the restatement. It records the transfer sent before the upgrade once, frozen as `stripe_custody`. A full-amount payout on the new version is refused (`must be positive`: no new funds while reservations stand). After the never-sent reservations are failed, the reissue equals them exactly and is paid, and sent plus reserved equals the payable. The latest version is A2's with the `$0` line, and the A1 versions are unchanged and still restated.
- **Gateway:** A2 submitted exactly once on the affected event (the reissue). A1 made no submission on it during the overlap.
- **Capture first:** A1's capture of B is paused inside its transaction. A2's paid recording waits on the event (over 1 s), then records the transfer sent before the capture and refuses one after it.

## Rollback

Never run down migrations in production. Each rollback below keeps every trigger in the database, and the code being rolled back to never removes them.

- **A2 → A1-R2 (or A1-R1).** Code only; the A2 migrations stay. A1 readers return, and A1 cannot finalize, create, release, submit or record outcomes on events with a classified capture, or record any payout as paid, because it writes no custody row. Both fail closed until A2 is redeployed. Frozen custody rows, `reader_digest` and the cutover stay; A1 ignores them. Release and submission on other events keep working.
- **A1-R2 → A1-R1.** Same schema. The submitter is inactive again, and the fence holds. An operation left `submitting` or `unknown` is adjudicated by lookup and is never resent by R1.
- **A1-R1 → 7bcd97c2.** Same schema; permitted only because the guards stay. Old code then cannot submit for fenced payments, cannot change a sale from a payment that does not own it, cannot count another payment's refunds in a sale's refund total, cannot submit, record as paid (even a transfer that left before the hold) or finalize on a held event, cannot pay out an event holding a second capture it acknowledged without classifying it (including one on an order already marked never fulfilled), cannot submit or record a payout while a capture on its event is in flight (refused at once, retry later), cannot finalize or create payouts on an event with a never-fulfilled order in a sale status (its calculator disagrees), cannot close an evidence hold by note, and cannot bind a fenced payment's refund. Each of those fails closed; refused webhooks stay `failed` with their signed receipts. Classification, holds and adjudication stop, and finance handles repayment through the reconciliation queue until R1 is redeployed. Old readers still show 7bcd97c2's CPA figures and admission rule (an open or lost dispute on any payment blocks admission) during that time; neither moves money.

Locally, the A1 migrations roll back cleanly (`db:migrate:down` removes the triggers, functions, table and columns) and reapply. That proves the schema round trip only. It is not a production procedure.
