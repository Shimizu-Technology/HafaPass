# Hosted backend deployment

The initial contract is `render.yaml`: only existing `hafapass-api` (`srv-d6bsuq0gjchc73fu35hg`), Singapore, Docker, explicit `0.5c-512mb` ($7 API tier), isolated staging and `HAFAPASS_RUNTIME=embedded`. No worker, clock or Redis service is created. Schema validation is not a completed sync or deployment. Verify the actual service ID and complete preview before applying; do not mutate an unrelated service.

Puma has one process, three request threads and Solid Queue 1.7.0's native supervised async runtime with one job thread. PostgreSQL stores jobs, delayed retries, recurring deduplication, progress and restart-safe hashed throttle counters. Start commands use the actual `RENDER_GIT_COMMIT` as `GIT_SHA`; the API's pre-deploy command alone owns migrations through the matching direct `DATABASE_MIGRATION_URL`. Docker paths are relative to `hafapass_api`, and `/up` is the platform boot-only health path.

Supply dedicated staging DB aliases, matching Clerk test identity/issuer, exact HTTPS frontend/API origins, persistent application secret (>64 characters) and RSA signing key (>=2048 bits), and the intended Sentry/S3 configuration privately. Do not copy legacy production secrets or data. See [Private testing runtime](PRIVATE_TESTING_STAGING.md) for exact fields. Test frontend builds use the matching public Clerk key, `/api/v1` API URL and actual free Netlify origin; no unowned domain is required.

Simulation is the default. Controlled provider transport additionally needs `HAFAPASS_PROVIDER_REHEARSAL=true`, selected `PROVIDER_REHEARSAL_SERVICES`, and the selected provider's private configuration: Stripe test keys/account identity/webhook/revision plus site setting `test`, or Resend key/verified sender/webhook/revision and 1–10 authorized recipients. The production capability gates are not approvals for rehearsal, and rehearsal is never production approval. Configure the actual public webhook paths `/webhooks/stripe` and `/webhooks/resend`, then prove signed receipt processing. Sender changes require restart because `MAILER_FROM_EMAIL` is loaded into the mail service.

Existing-service `sync: false` entries are not new secret provisioning; manually verify/populate the encrypted store. Do not depend on a green `/up` for release acceptance. Verify current-release executor/scheduler heartbeats, actual successful ticks, no overdue/stalled work, appropriate role boundaries, hosted delivery/provider outcomes, backups, alerts and the scoped S3 journey. Confirm the deployed commit and matching frontend after the release.

The optional `render.sidekiq.yaml` retains the old extra-service topology for a separately approved future deployment. A preferred first extraction uses `HAFAPASS_RUNTIME=solid_queue` on API and one SQL worker running `bundle exec bin/jobs`, consuming the same database without a new Redis or separate clock. Do not switch adapters while queued/delayed/claimed work remains. Full capacity, recovery and cutover rules are in [Single-service durable runtime](SINGLE_SERVICE_RUNTIME.md).

Render's current [pricing](https://render.com/pricing) lists the API/worker `0.5c-512mb` at $7/month. Database usage, email, storage, bandwidth/build overages and workspace fees are separate. Polling may keep Neon compute active. This document does not authorize or claim provisioning, deployment, real-money operations or completion of external acceptance.
