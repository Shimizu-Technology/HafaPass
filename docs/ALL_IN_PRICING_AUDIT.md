# All-in ticket pricing audit

Checked against `origin/main` at `249ec345` and this branch on 2026-10-22, using the [FTC rule FAQ](https://www.ftc.gov/business-guidance/resources/rule-unfair-or-deceptive-fees-frequently-asked-questions). The ticket total is the unit ticket price plus the buyer's share of the mandatory service fee. `Commerce::ServiceFee` is the source of truth for API quotes and checkout; the frontend reads those quotes. Its fee is rounded per ticket, then the event's `buyer_fee_percent` is applied. `buyer_pays`, `organizer_absorbs`, and `split_fees` are covered by request specs. Card processing is paid by the platform or deducted from organizer proceeds, never added to the buyer after the advertised total. There is no separate buyer processing charge. Optional catalog add-ons appear separately in checkout. No government tax is currently added to these ticket totals.

`SiteSetting` changes to fee percentage, flat fee, processing bearer, or payout timing are scheduled with an effective instant and advance notice. The active row is switched on the first settings read at or after that instant; prior orders retain their snapshots. The admin preview counts affected organizers before confirmation, each active owner receives a durable notice, and owners can acknowledge a dashboard banner without blocking sales. Changing material terms changes the policy registry digest at activation. Production checkout pauses until an administrator approves the new register, so activation needs a monitored approval window.
